# Границы и контракты

## От правил к владельцам

Для каждого важного действия установи:

| Вопрос | Что зафиксировать |
| --- | --- |
| Что нельзя нарушить? | Инвариант и условия конкурентного выполнения |
| Кто принимает окончательное решение? | Владелец авторитетного состояния |
| Что меняется атомарно? | Агрегат и локальная транзакция |
| Что может отставать? | Проекция, кэш, индекс, внешнее уведомление |
| Кто и как восстанавливает состояние? | Источник для сверки/пересборки, ответственный компонент |

Агрегат определяется совместной согласованностью правил. Он не обязан совпадать с таблицей или сервисом. Например, сумма заказа выводится из его строк, но фактический складской остаток принадлежит складу. Заказ не может гарантировать чужой инвариант локальной проверкой своей структуры.

Разные входы — HTTP, Kafka, импорт — должны приводить к одному правилу предметной области. Проверка формата относится к адаптеру; бизнес-правило должно сохраняться независимо от входа.

## Выбор границы сервиса

Сопоставь совместно изменяемые правила, владение команды, требования к развёртыванию, профили нагрузки и изоляцию отказов. Учитывай цену сети, совместимости, наблюдаемости, CI/CD и дежурства.

Один сервис может содержать несколько модулей. Один bounded context не требует отдельного процесса автоматически. Если пользователь уже выбрал микросервисы, работай в этом ограничении и покажи конкретные последствия границ, не заменяя задачу без согласования.

Общая физическая PostgreSQL-инсталляция возможна при логическом разграничении владельцев и прав, но связывает ресурсы и отказоустойчивость. Это отличается от общей схемы с произвольной записью всех сервисов во все таблицы.

Порты и адаптеры помогают удержать бизнес-модель независимой от транспорта и хранения. Применяй их там, где есть настоящая граница; структуру каталогов оценивай по импортам и ответственности, а не по названиям слоёв.

## Команда, событие, запрос

- Команда просит владельца выполнить действие и может быть отклонена. `CreateOrder` — намерение, даже если оно уже в Kafka.
- Событие `OrderCreated` сообщает через брокер о созданном заказе. Внешний клиент не получает права объявить факт успешной операции только выбором имени сообщения.
- Запрос получает представление и не должен незаметно выполнять бизнес-команду.
- CDC-запись отражает изменение хранения; её форма и гарантии могут отличаться от контракта события, которое публикует сервис.

Зафиксируй версии схемы, обязательные поля, пределы размера и допустимые неизвестные поля. Разделяй внешний DTO, внутреннюю модель и событие, когда их эволюция различается. Не распространяй общий пакет с внутренним бизнес-агрегатом между сервисами ради удобства импортов.

## Семантика ответа

Примеры возможных контрактов, которые нужно адаптировать к API проекта:

| Результат | Что означает |
| --- | --- |
| `201 Created` в DB-first сценарии | Владелец зафиксировал объект, квитанцию и Outbox в своей транзакции |
| `202 Accepted` в Kafka-first сценарии | Команда надёжно принята выбранной очередью; бизнес-результат ещё неизвестен |
| Квитанция `{id, version, status}` | Исторический результат этой команды, не актуальная карточка навсегда |
| Таймаут после отправки | Исход может быть неизвестен; нужен запрос статуса или безопасный повтор |

HTTP-коды сами по себе не задают всю бизнес-гарантию. Для `202` укажи способ получить результат и ошибки команды. Для успеха записи не обещай немедленную доступность в асинхронной витрине.

## Идентификаторы и версии

Разделяй:

- ID сущности — идентичность бизнес-объекта;
- ID команды / idempotency key — идентичность намерения и его повторов;
- ID события — идентичность конкретного факта;
- schema version — формат сообщения;
- aggregate version — порядковое изменение конкретного агрегата;
- expected version — предпосылка для оптимистической записи;
- min version — требование к свежести чтения одного агрегата;
- broker partition/offset — техническая позиция в логе.

Ключ идемпотентности ограничь арендатором и выбранной областью операции. Повтор того же ключа с изменённой операцией или содержимым должен иметь явный конфликт. Повтор с тем же смыслом возвращает сохранённый результат без нового эффекта.

Нормализацию и хеширование запроса определи как контракт: учитывай операцию, значимые поля, правила чисел и необязательных значений. ID сущности может генерировать клиент или сервер. При серверной генерации сохрани выбранный ID в той же атомарной границе и повторно возвращай его; не генерируй новый ID для каждой попытки одной команды.

## Межсервисные процессы

Если правило требует нескольких владельцев, не выдавай последовательность HTTP-вызовов за общую ACID-транзакцию. Определи состояния процесса, таймауты, идемпотентность участников, восстановление и допустимые компенсации. Компенсация — новая бизнес-операция; она может не полностью обратить последствия и сама требует обработки отказов.

Сначала проверь, действительно ли нужна распределённая граница. Saga, оркестрация или хореография имеют смысл после определения процесса и ответственности, а не вместо них.
