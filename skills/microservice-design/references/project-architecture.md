# Архитектурные соглашения команды

## Границы сервисов

Разделяй микросервисы строго по DDD. Для каждой операции определи ограниченный контекст, владельца данных и бизнес-инвариант, который этот владелец обеспечивает. Если для одного инварианта двум сервисам постоянно нужна общая транзакция, пересмотри границу. Другие контексты получают данные владельца через его контракт или из событий.

## E2E-проверки сервисов

Для каждого backend-сервиса пиши только E2E-тесты. Выбирай сценарии по БТ и бизнес-правилам сервиса, проходи их через штатную точку входа и проверяй наблюдаемый результат. Для библиотек `common` виды тестов выбирай по соглашениям самой библиотеки.

Для каждого бизнес-правила определи вход и ожидаемый исход. В пользовательском сценарии начни с запроса к шлюзу, во внутреннем — с вызова gRPC или доставки сообщения брокером. Если успех операции включает изменения в нескольких сервисах, проследи сценарий до результата у последнего участника. Если потребитель гарантирует идемпотентность, доставь одно событие дважды и проверь через API потребителя, что изменение произошло один раз.

## Имена и каталоги доменной модели

Группируй код внутри Domain по предметной области, которой принадлежит поведение. Например, в каталоге `Order/` вместе лежат `Order.cs`, `OrderLine.cs` и `OrderStatus.cs`. Тип получает имя из согласованной модели предметной области, а файл и пространство имён указывают на этот тип и его каталог. Сущности, объекты-значения и перечисления одного сценария остаются рядом.

В агрегате держи редактируемые данные в именованных доменных типах. За сериализацию отвечают транспорт и слой хранения.

## Gateway и gRPC

Внешний клиент обращается к gateway. Когда ответ зависит от немедленного результата микросервиса, gateway вызывает его по gRPC. То же правило действует для синхронного вызова между микросервисами. Для маршрута укажи входной HTTP-контракт, метод gRPC и ответ, который gateway возвращает клиенту. Решение о допустимости изменения принимает доменный сервис, который владеет данными.

Для gRPC называй действие вместе с объектом, например `CreateItem`. Вход и результат этой операции называй `CreateItemRequest` и `CreateItemResponse`. Каждый RPC, сообщение и поле снабжай кратким комментарием. В многострочных сообщениях отводи каждому полю отдельную строку.

## RabbitMQ для изменений

Предпочитай асинхронное взаимодействие через RabbitMQ везде, где вызывающей стороне не нужен немедленный результат. Основной случай — реакция других сервисов на уже совершившееся изменение. Владелец фиксирует изменение и исходящее событие в одной транзакции через Outbox. В обработчике команды на EF Core собери изменения сущностей и записи Outbox в одном DbContext. В конце записи один раз вызови `await context.SaveChangesAsync(cancellationToken)`. Это граница атомарной записи. Не открывай транзакцию вручную через `BeginTransactionAsync` или `TransactionScope`. Чтение и повтор без изменений не требуют сохранения. Подписчики обрабатывают событие независимо и учитывают повторную доставку. Если клиенту нужен результат записи, владелец возвращает его по gRPC, а реакции подписчиков по-прежнему идут через RabbitMQ.

## Redis для GET

Для большинства GET, возвращающих редко меняющиеся данные, используй Redis. Справочник или перечень опубликованных категорий обычно подходит, если допустима оговорённая задержка обновления. При промахе прочитай данные у владельца и заполни кеш. Выбирай TTL по допустимой давности ответа. Если обновление должно появиться раньше, инвалидируй или обновляй запись по событию изменения.

Ключ должен различать параметры запроса и область видимости ответа, включая пользователя или арендатора, когда результат персонализирован. Если операция требует актуального состояния сразу после записи, читай его у владельца либо обеспечь нужную свежесть перед выдачей кешированного ответа.

## Файлы через s3-storage

Для загрузки, получения и удаления файлов используй контракт `s3-storage`. Хранилище отвечает за содержимое, метаданные и доступ к объектному хранилищу. Доменный сервис хранит `FileBinding` из `common` и отвечает за связь файла со своей сущностью.

Например, при скачивании вложения доменный сервис проверяет доступ пользователя к сущности. По идентификатору из `FileBinding` он запрашивает файл или ссылку способом, который предоставляет контракт хранилища.
