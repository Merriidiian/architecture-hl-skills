# Архитектурные соглашения проекта

## Границы сервисов

Разделяй микросервисы строго по DDD. Для каждой операции определи ограниченный контекст, владельца данных и бизнес-инвариант, который этот владелец обеспечивает. Если для одного инварианта двум сервисам постоянно нужна общая транзакция, пересмотри границу. Другие контексты получают данные владельца через его контракт или из событий.

## Gateway и gRPC

Внешний клиент обращается к gateway. Когда ответ зависит от немедленного результата микросервиса, gateway вызывает его по gRPC. То же правило действует для синхронного вызова между микросервисами. Для маршрута укажи входной HTTP-контракт, метод gRPC и ответ, который gateway возвращает клиенту. Решение о допустимости изменения принимает доменный сервис, который владеет данными.

## RabbitMQ для изменений

Предпочитай асинхронное взаимодействие через RabbitMQ везде, где вызывающей стороне не нужен немедленный результат. Основной случай — реакция других сервисов на уже совершившееся изменение. Владелец фиксирует изменение и исходящее событие в одной транзакции через Outbox. Подписчики обрабатывают событие независимо и учитывают повторную доставку. Если клиенту нужен результат записи, владелец возвращает его по gRPC, а реакции подписчиков по-прежнему идут через RabbitMQ.

## Redis для GET

Для большинства GET, возвращающих редко меняющиеся данные, используй Redis. Справочник или перечень опубликованных категорий обычно подходит, если допустима оговорённая задержка обновления. При промахе прочитай данные у владельца и заполни кеш. Выбирай TTL по допустимой давности ответа. Если обновление должно появиться раньше, инвалидируй или обновляй запись по событию изменения.

Ключ должен различать параметры запроса и область видимости ответа, включая пользователя или арендатора, когда результат персонализирован. Если операция требует актуального состояния сразу после записи, читай его у владельца либо обеспечь нужную свежесть перед выдачей кешированного ответа.

## Файлы через s3-storage

Для файлов проекта единственная точка доступа к хранилищу — `s3-storage`. Через него проходят загрузка, получение и удаление. Только этот сервис обращается к S3. Когда файл связан с бизнес-объектом, доменный сервис хранит ссылку на файл по контракту `s3-storage`. Способ передачи содержимого определяет тот же контракт.
