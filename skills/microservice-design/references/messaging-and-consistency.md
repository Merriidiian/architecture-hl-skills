# Доставка, идемпотентность и согласованность

## Выбор пути записи

DB-first удобен, когда ответ должен подтверждать уже выполненное бизнес-изменение. Kafka-first удобен для устойчивого асинхронного приёма и сглаживания пиков. Для второго варианта нужны наблюдаемый результат команды, ограничение backlog и понятная задержка выполнения.

Брокер не создаёт бесконечную пропускную способность: при долговременном превышении входа над обработкой растут lag, задержка и расход диска. Отдельно определи admission control и поведение при исчерпании ресурсов.

## Outbox

На стороне владельца записи:

```text
BEGIN
  установить проверенный tenant-контекст, если он нужен
  занять ключ команды либо получить сохранённую квитанцию
  проверить инварианты и изменить бизнес-состояние
  записать исходящее событие с устойчивым event_id
  сохранить результат команды
COMMIT
```

Запись состояния и отправка в брокер двумя независимыми действиями оставляют окно потери события или публикации незафиксированного факта. Outbox переносит сетевую публикацию за локальную атомарную границу.

После успешной отправки relay может упасть до отметки публикации. Повторная отправка того же события ожидаема: это at-least-once, даже при идемпотентном Kafka producer. Не обещай end-to-end exactly-once между Kafka и произвольной внешней БД.

Для polling relay:

- Захватывай ограниченный batch короткой транзакцией, например с lease и `FOR UPDATE SKIP LOCKED`.
- Публикуй после освобождения SQL-транзакции. Не держи соединение и row locks на время произвольного сетевого ожидания.
- Подтверждай результат только при сохранённом владении: проверяй lease token/поколение. Запоздавший worker не должен перезаписать состояние нового владельца.
- Продумай истечение lease, размер batch, backoff, очистку и возраст самой старой записи.
- Для строгого порядка не допускай публикацию следующей версии агрегата, пока предыдущая не завершена по выбранному протоколу.

Lease допускает перекрытие старого и нового работника после паузы процесса. Проверка токена защищает отметку в БД, но не отменяет уже выполненную внешнюю отправку: дубликаты по-прежнему возможны.

Polling и CDC — альтернативы с разной эксплуатационной ценой. Для CDC учитывай доступность коннектора, replication slot, удержание WAL, совместимость и процедуру восстановления. CDC не устраняет необходимость контракта событий и идемпотентного потребителя.

## Inbox и подтверждение

На стороне потребителя:

```text
получить сообщение
BEGIN в локальной БД
  проверить envelope, доверенный источник и область tenant
  зарегистрировать (tenant, consumer, event_id) и отпечаток
  при новом событии применить эффект/проекцию и сохранить позицию
COMMIT БД
подтвердить сообщение или broker offset
```

Сохраняй Inbox и эффект вместе. Ранняя отдельная запись Inbox способна потерять эффект, поздняя — допустить повторный эффект. Одинаковый ID с другим значимым содержимым — нарушение контракта, а не безобидный дубликат.

Для внешнего побочного эффекта, например платёжного API, локального Inbox недостаточно: нужен контракт идемпотентности внешнего вызова или отдельный устойчивый процесс.

При параллельной обработке Kafka нельзя коммитить offset за ещё не завершённую более раннюю запись той же партиции. Сохраняй непрерывный подтверждённый префикс. При revoke останови выдачу работы, заверши/отмени незавершённое и не подтверждай неподтверждённый эффект.

## Порядок и ошибки

Ключ Kafka задаёт выбор партиции. Он не исправит перепутанный порядок двух relay и не создаёт общего порядка между партициями. Задай ключ с учётом tenant и aggregate ID, конкуренцию издателей и правила версий.

| Ситуация | Возможная политика |
| --- | --- |
| Тот же event ID и содержимое | Безопасно вернуть уже зафиксированный результат |
| Временная недоступность БД | Ограниченные попытки/пауза, без раннего подтверждения |
| Бизнес-отказ команды | Устойчивый результат отказа по контракту команды |
| Неподдерживаемая схема, изменённый payload под тем же ID | Карантин/остановка с диагностикой и владельцем восстановления |
| Разрыв версии у проекции, требующей непрерывность | Не применять следующую версию молча; буферизация или остановка с восстановлением |

DLQ/карантин должны иметь owner, alert, retention и процедуру replay/fix/skip. Пропуск версии допустим лишь при явно спроектированной семантике проекции; для зависимых дельт он может навсегда исказить результат. Snapshot-событие иногда допускает другую стратегию, но это отдельный контракт.

## CQRS и чтение своих записей

Разделение команд и запросов может быть логическим внутри одного приложения. Отдельные сервисы, БД и брокер нужны только если их цена оправдана.

Проекция принадлежит читающей стороне. Её можно оптимизировать под запросы и пересобрать из определённого источника; это не обязательно event sourcing. Наличие Outbox само по себе не означает полную историю для восстановления после очистки.

Для read-your-own-writes карточка может принимать минимальную версию агрегата. Если витрина отстаёт, API возвращает документированный ответ «ещё не готово» с ограниченным polling/ожиданием. В OrderFlow это `409` с машинным кодом `projection_not_ready` и `Retry-After`; это пример, а не универсальный HTTP-стандарт.

Отдельно различай отсутствие объекта, отставание проекции и недоступность хранилища. Версия одного объекта не задаёт свежесть всего списка. Для списка нужны свои критерии, watermark/позиция или оговорённая eventual consistency.

Пагинация по стабильному уникальному ключу с ограничением страницы предсказуемее глубокого `OFFSET`. Сохраняй фильтры и tenant в курсоре/запросе. Несколько HTTP-страниц не образуют единый snapshot автоматически.

Основы: ПКП-5–7, РХД-3–6, `orderflow-cqrs` и `teamboard-cqrs`.
