# Нагрузка, отказоустойчивость и эволюция

## Измеримая исходная точка

Перед масштабированием опиши набор операций, долю чтения/записи, размеры данных, распределение по tenant/ключам, горячие ключи, конкурентность, интенсивность входа и длительность пика. Укажи окно и условия SLO, latency p95/p99, throughput, ошибки и насыщение ресурсов.

Генератор с фиксированными workers и следующим запросом только после ответа сам замедляет вход при перегрузке. Такой закрытый контур полезен для baseline, но может скрывать очередь и хвосты задержек реального независимого входа. Укажи метод измерения и ограничения вывода.

Не сравнивай результаты с разными данными, ресурсами, прогревом и конкурентностью без объяснения. Не усредняй p95 разных узлов как общий p95: агрегируй пригодные распределения/гистограммы.

## Синхронные зависимости

- Выдели общий deadline и бюджеты последовательных этапов. Добавь предел соединений, ожидания пула и числа активных вызовов.
- Повторяй лишь подходящие временные ошибки при безопасной семантике операции. Общий deadline ограничивает все попытки вместе; backoff и jitter уменьшают синхронные повторные атаки на зависимость.
- Не назначай retries независимо на каждом слое без расчёта их перемножения. Определи владельца повторов.
- Bulkhead ограничивает взаимное влияние зависимостей/арендаторов. Circuit breaker имеет смысл при подходящем профиле отказа; опиши открытие, проверочные вызовы и восстановление.
- Таймаут изменяющей операции оставляет неопределённость результата. Идемпотентность и запрос статуса важнее слепого повторения.

## Матрица частичных отказов

Для каждого обещания перечисли условия и проверку. В DB-first CQRS типичные цели:

| Сбой | Ожидаемое поведение при выполнении условий |
| --- | --- |
| Брокер недоступен | Команды фиксируются с Outbox, пока есть допустимая ёмкость и backlog |
| Сервис записи недоступен | Чтение существующей локальной проекции продолжается |
| Сервис чтения недоступен | Владелец продолжает фиксировать команды в пределах ресурсов |
| Потребитель упал после COMMIT БД | Повтор сообщения не повторяет эффект |
| Relay упал после broker ack | Повторная публикация безопасна для потребителя |
| Сбой в середине локальной транзакции | Откатываются состояние, квитанция и событие вместе |

Одно успешное испытание не доказывает всю матрицу. Управляемые точки сбоя и проверка сохранённых данных полезнее случайного перезапуска без контроля фазы. Для тестов используй изолированную среду и имеющееся разрешение; не останавливай рабочие сервисы ради демонстрации.

Наблюдай задержку проекции, lag и возраст Outbox, число повторов/карантина, насыщение пулов, блокировки и ошибки контрактов. Разделяй техническое здоровье процесса и способность обслужить конкретный путь работы.

## Совместимость и миграции

Планируй одновременную работу старой и новой версии: сначала расширение совместимой схемы, затем совместимый код, заполнение/проверка, переключение и только потом удаление старого контракта. Срок этапов определяется фактическими потребителями, а не одним релизом.

Для события определи совместимые добавления, обязательность полей и версию схемы. Не переиспользуй поле с новым смыслом. Тестируй старого потребителя на новых допустимых сообщениях и нового — на сохранённых старых.

Для пересборки витрины укажи источник, сохранённый горизонт истории, исходную позицию, параллельный catch-up, проверку инвариантов и атомарное переключение поколения. Не обнуляй рабочую проекцию и offset без процедуры восстановления.

Уточни RPO/RTO и проверку восстановления резервных копий, если это часть задачи. Read replica и Kafka сами по себе не заменяют резервное копирование и восстановление.

## Масштабирование хранения

| Мера | Что может решить | Что остаётся |
| --- | --- | --- |
| Запросы, индексы, лимиты пула | Неэффективный доступ и лишняя конкуренция | Пределы одного узла |
| Кэш/витрина | Часть повторяющихся чтений | Инвалидация и свежесть |
| Реплики чтения | Нагрузка чтения | Запись на primary, lag |
| Секционирование PostgreSQL | Управление объёмом, pruning и обслуживание | Общие CPU/WAL/отказ primary |
| Вертикальное разделение | Независимые группы данных | Межгрупповые транзакции |
| Горизонтальный шардинг | Часть пределов записи, хранения и изоляции | Маршрутизация, skew, перенос и межшардовые операции |

Для ключа шардинга оцени локальность транзакций, равномерность, стабильность, доступность ключа до запроса и переносимость. `tenant_id` полезен для B2B, но не решает проблему одного слишком крупного tenant или глобального поиска без tenant.

Размещай связанные первичные данные, журнал команд и Outbox одного tenant совместно. Глобальный каталог размещения относится к control plane. Не обещай обычные FK/ACID между независимыми шардами.

Виртуальные бакеты отделяют стабильное распределение ключей от числа физических серверов. `hash % число_серверов` массово меняет маршруты при изменении этого числа. Go `hash/maphash` не годится для постоянного межпроцессного маршрута: зафиксируй алгоритм, представление входа, endian, число бакетов и тестовые векторы.

Кэш топологии публикуй согласованным неизменяемым снимком с версией. План переноса должен иметь состояние миграции, копирование, catch-up/проверку, переключение и fencing, запрещающий запись по устаревшему маршруту. Обычный TTL кэша и consistent hashing этого не обеспечивают. Сохранённый локальный снимок помогает доступности только в пределах явно безопасного состояния.

Основы: РХД-1, РХД-4–7, ПКП-1, ПКП-3–7. Нагрузочные числа и хеш по модулю 128 в лекциях — параметры конкретного стенда.
